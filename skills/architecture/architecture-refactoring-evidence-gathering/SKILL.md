# Refactoring Evidence Gathering Instructions

When supporting the measurement of a refactoring candidate's starting
state, use this tool to gather concrete, citable evidence across several
distinct categories — complexity, test/type coverage, version-control
history, documentation, and reputation — rather than asserting that code
"looks bad" without a measured basis.

---

## Purpose

This tool helps the AI assistant by:

- establishing that a refactor's success metric must track the *specific*
  pain point it addresses, since a behavior-preserving refactor is by
  definition invisible to users and won't move most business/health
  metrics regardless of outcome,
- providing cheap, static, non-executing techniques for estimating code
  complexity (cyclomatic-style decision-point counting, size proxies,
  inline comment density) as a practical alternative to tooling that
  requires running or installing something,
- treating test coverage adequacy as both a quantitative number and a
  qualitative judgment (reliable, resilient, varied), since a suite that's
  merely high-percentage isn't automatically a trustworthy safety net for
  a refactor specifically,
- surfacing what version-control history can reveal beyond simple churn —
  commit-message patterns, complexity trends over time, hidden temporal
  coupling between files, and authorship fragmentation — as techniques
  drawn from Adam Tornhill's *Software Design X-Rays*,
- treating documentation and team reputation as real evidence sources,
  scoped honestly to what's actually reachable versus what should be
  recommended as a follow-up requiring human interaction,
- recommending roughly one metric per category rather than mechanically
  reporting every available signal, since the goal is the strongest case
  for a specific candidate, not exhaustiveness.

---

## Expected outcome

As the AI, your response should help teams adopt an approach that:

- names, for every refactoring candidate, the specific metric that would
  show success — never just "the code will be cleaner" — and treats
  performance-motivated candidates as the easy case, since a natural
  before/after metric (latency, memory, query count) usually already
  exists from normal monitoring,
- computes complexity signals cheaply and statically, without requiring
  new tooling to be installed or run, and reads existing complexity
  reports if the project already generates them rather than duplicating
  that work,
- assesses test/type coverage on both axes — quantitative percentage and
  qualitative reliability/resilience/variety — flagging near-100%
  coverage as worth a second look rather than an automatic green light,
- mines version control for commit-message patterns, complexity trends,
  temporal coupling, and authorship fragmentation, filtering out known
  sources of false signal (config/autogenerated files, inconsistent
  commit granularity) before trusting the result,
- gathers documentation and reputation evidence honestly — reading what's
  actually reachable as files, and explicitly recommending (rather than
  fabricating) evidence that would require a live human interaction (chat
  history search, interviews, surveys) to actually collect,
- builds a complete picture selectively: roughly one metric per category,
  chosen for what best supports the specific candidate's case.

## Instructions for the AI

1. **Pick the metric that tracks the actual pain point, not a generic health score**
   - A successful refactor is invisible to users and behavior-preserving —
     most business/user-facing metrics won't move as a result of one, and
     won't move even if the refactor is a total success. Choosing a
     metric orthogonal to the actual problem produces a case that can't
     show whether the work paid off.
   - For each candidate, name the specific measurement that would show
     success (a complexity score dropping, a churn area's bug rate
     falling over the following months, coverage rising).
   - **Performance-motivated candidates are the one exception worth
     calling out explicitly**: they're the easiest of all to measure,
     since a natural before/after metric usually already exists from
     normal monitoring — cite it directly rather than inventing a proxy.

2. **Use cheap, static complexity signals**
   - **Cyclomatic-style counting** — count decision points per function
     (`if`, `elif`/`else if`, `for`, `while`, `case`/`match` arms, boolean
     `and`/`or`/`&&`/`||` in a condition), starting from 1. This is a
     grep-computable approximation of McCabe's cyclomatic complexity — a
     rough lower bound on how many test cases a function needs, and a
     fast way to rank functions within a hotspot. A handful of sequential
     checks (complexity ~3–5) is unremarkable; a function deep in double
     digits is a strong candidate on its own.
   - **Size proxies** — logical lines of code (excluding blank
     lines/pure comments) per file, and function length, are a cheap
     stand-in when finer-grained complexity metrics aren't practical to
     compute. An unusually long file or function is worth flagging on
     size alone even before deeper analysis.
   - **Inline comment density per function** — developers tend to leave
     explanatory inline comments specifically where the surrounding logic
     is hard to follow. A function with an unusually high concentration
     of inline comments (not doc blocks) is worth flagging as a probable
     complexity hotspot even without a formal score.
   - Don't rely on a single complexity signal in isolation, and don't
     expect every legitimate refactor to move these numbers — some
     complexity is inherent to real business logic and won't (and
     shouldn't) disappear. Reserve complexity-metric-driven
     prioritization for candidates whose actual goal is untangling logic;
     use a different metric (size, duplication, naming, coverage) when
     the goal is readability, testability, or consolidation instead.
   - Prefer reading an already-generated complexity report (a checked-in
     file, a CI artifact) over computing one from scratch, and prefer
     grep-based static counting over newly installing or running a
     complexity-analysis tool.

3. **Assess test coverage quantitatively and qualitatively**
   - **Quantitative**: read and cite an existing coverage report/artifact
     if one exists, rather than computing coverage by running the test
     suite. As a rule of thumb, healthy coverage on genuinely well-tested
     code tends to sit around 80–90%; treat coverage at or near 100% as
     worth a second look rather than an automatic green light, since it's
     an easy number to reach with shallow, box-checking tests that assert
     little.
   - **Qualitative** (sample, don't exhaustively verify): are the tests
     *reliable* (deterministic pass/fail, not flaky), *resilient*
     (asserting behavior, not implementation details — this matters
     specifically for refactoring, since a test suite tightly coupled to
     internal structure will itself need rewriting alongside the
     refactor, defeating its purpose as a behavior-preservation check),
     and *varied* (a mix of unit/integration/end-to-end, not all one
     level of fidelity)?
   - For legacy code with no tests at all, retrofitting coverage via
     *seams* (points where behavior can be verified or substituted
     without modifying the code itself, per Michael Feathers' *Working
     Effectively with Legacy Code*) is the standard technique for
     building a safety net before refactoring.
   - A candidate with no safety net, or with implementation-coupled
     tests, is materially higher-risk than one with genuine behavioral
     coverage — factor this explicitly into sequencing (build/strengthen
     the safety net first).

4. **Assess type coverage for a gradually-typed codebase**
   - Low type coverage in a candidate area is a weaker second safety net,
     not just a style gap — types catch a different class of bug than
     tests do.
   - As a rough reference point, a gradually-typed codebase sitting above
     roughly 95% type coverage is in good shape; 100% is rarely realistic
     or necessary.

5. **Mine version control beyond simple churn counts** (techniques from
   Adam Tornhill's *Software Design X-Rays*, worth citing when used)
   - **Change frequency** (churn) — files/modules changed most often over
     a meaningful recent window are the strongest available signal for
     *where* a refactor pays off soonest; change frequency tends to
     follow a power distribution, with a disproportionate share of
     changes concentrated in a small subset of files.
   - **Commit message search** — searching commit messages for keywords
     tied to a suspected problem area (an error type, a domain term, a
     ticket prefix) surfaces a concrete set of commits supporting or
     refuting a hypothesis about what's been going wrong there.
   - **Complexity trend, not just a snapshot** — for a strong candidate,
     sample its complexity/size metric at a few points through its
     history rather than only the current state. A file whose complexity
     has been monotonically climbing is stronger evidence than the same
     score in isolation, and re-sampling after a refactor (confirming
     both the score *and* the change frequency dropped) is the concrete
     way to confirm the refactor paid off.
   - **Temporal coupling** — files frequently modified together in the
     same commit, even with no direct import/reference between them,
     signal hidden coupling. Compute file-pair co-occurrence frequency
     across commits for a suspected area. Some coupling is legitimate (a
     source file and its test), but unexplained coupling between
     otherwise-unrelated files often indicates a leaky abstraction or
     copy-pasted logic worth consolidating. Filter out config/
     autogenerated files and single-huge-commit outliers before trusting
     this signal — commit granularity varies a lot by developer habit,
     and that variance produces false positives if taken at face value.
   - **Authorship fragmentation** — a file with many distinct minor
     contributors (as opposed to a small, consistent set of maintainers)
     correlates with higher defect risk, plausibly from coordination
     overhead and individual unfamiliarity with the whole. Use this as a
     risk signal for *prioritizing* a candidate — never as a reason to
     gate who may work on it. If a team treats collective, continuous
     refactoring as a norm rather than gating work by ownership, this
     signal reinforces the case *for* a well-organized, properly reviewed
     effort — replacing the pattern of isolated, uncoordinated changes
     that produced the fragmentation in the first place, not narrower
     ownership going forward.

6. **Gather documentation and reputation evidence honestly**
   - **Documentation**: read what's actually reachable — READMEs,
     `/docs`, architecture decision records, a linked postmortem/incident
     doc, a CHANGELOG. A technical spec that already documents a known
     limitation is strong, pre-existing evidence a candidate is worth
     addressing. If postmortem documents are accessible, search their
     "Contributing Factors"/"What Went Wrong" sections for the candidate
     area, and cite an incident count if more than one names it.
   - Evidence that lives in chat history, email, or a project-management
     tool without a file-based export is often out of reach for static
     inspection. When a candidate's case would clearly benefit from that
     kind of search, **recommend it as a follow-up** (naming the
     suggested keywords/area) rather than claiming to have gathered it.
   - **Reputation**: a codebase area's reputation among the team (dread,
     jokes, "don't touch that file") is real evidence, but collecting it
     requires talking to people. Recommend a short set of interviews or a
     brief closed-form survey (a handful of scaled/multiple-choice
     questions beats several open-ended ones for response rate) with
     developers spanning a range of tenure and familiarity, asking about
     the area's impact on their ability to develop, test, debug, and
     review changes there. A strong reaction from someone without deep
     familiarity with the code is itself signal. Reputation can also
     affect retention — engineers avoiding or leaving a team over a code
     area's condition is a compelling, if hard-to-collect, data point.

7. **Build a complete picture, but selectively**
   - Don't mechanically report every metric from every category. For each
     candidate, aim for roughly one metric per category (complexity, test
     coverage, documentation/version-control evidence, reputation if
     gathered) — no single metric characterizes a refactor's full value
     on its own, but exhaustiveness isn't the goal either.
   - Prefer the subset of evidence that most directly supports the
     specific candidate's case and has the best realistic chance of
     showing measurable improvement afterward — that's what actually
     makes the case to a reader deciding whether to invest in it.

## AI decision guidance

When generating refactoring-evidence guidance, keep these principles in
mind:

- **Match the metric to the actual pain point** — a metric orthogonal to
  the problem can't show whether the work succeeded.
- **Prefer cheap, static, non-executing techniques** over installing or
  running new analysis tooling — read existing reports if they exist.
- **Coverage adequacy is quantitative and qualitative** — a high
  percentage alone doesn't make a test suite a trustworthy safety net.
- **Version-control history holds more than churn** — commit-message
  patterns, complexity trends, temporal coupling, and authorship
  fragmentation are all minable with `git log`.
- **Be honest about what's actually reachable** — recommend gathering
  documentation/reputation evidence that requires human interaction
  rather than fabricating it.
- **Select evidence, don't dump it** — roughly one metric per category,
  chosen for the strongest case, not maximal coverage of every signal.

---

## Success criteria

A strong response should ensure that it:

- **names a specific success metric matched to the pain point** for every
  candidate,
- **computes complexity/size signals cheaply and statically**, reading
  existing reports where available,
- **assesses test/type coverage on both quantitative and qualitative
  axes**,
- **mines version control for more than churn** — commit messages,
  complexity trend, temporal coupling, authorship — with known false-signal
  sources filtered out,
- **scopes documentation/reputation evidence honestly**, distinguishing
  what was actually gathered from what's recommended as a follow-up,
- **selects a focused subset of evidence per candidate**, not an
  exhaustive dump.

## Example prompts for the AI

- "How do we know if this refactor actually worked?"
- "Is this function's test coverage good enough to refactor safely?"
- "Which files in this repo are hiding tightly coupled logic we don't
  know about?"
- "What evidence would convince management this refactor is worth doing?"
