# Architecture

Enterprise/solution architecture practices: diagramming techniques (domain storytelling, roadmaps, stakeholder maps, portfolio diagrams), risk management, resilient system design, platform strategy, and technology standards adoption.

Cross-cutting — not tied to a specific codebase or stack. Most teams install this globally (`-g`) rather than per-project.

## Install

```bash
npx skills add mihailtd/skills/skills/architecture --all
```

Add `-g` to install globally instead of per-project. Use `--skill <name>` (repeatable) instead of `--all` to cherry-pick individual skills from this package, e.g.:

```bash
npx skills add mihailtd/skills/skills/architecture --skill architecture-building-with-failure-in-mind
```

- **[architecture-evolution-cadence](architecture-evolution-cadence/SKILL.md)** — Treating architectural-vision change as rare and deliberate: testing technology-driven change for real market impact, weighing switching costs honestly against sunk operational expertise, and using a regular, calendar-aligned review cycle as both a decision point and a relief valve for ad hoc pressure to change.
- **[architecture-change-proposals](architecture-change-proposals/SKILL.md)** — Capturing every proposed change as a lightweight, progressively elaborated change proposal spanning motivation, concept, and detail; tracked in an architectural backlog distinct from the product backlog; closed out by redocumenting the system once implemented.

- **[architecture-composition](architecture-composition/SKILL.md)** — Designing decomposed elements with recomposition in mind from the start: simple, efficient relationships, interaction granularity matched to interface cost, standardized wiring mechanisms, and (for platforms) balancing standards-as-constraint against flexibility for unanticipated combinations.
- **[architecture-incremental-design](architecture-incremental-design/SKILL.md)** — Working a decomposed design incrementally — solving and recomposing a subset of the tree into working form before expanding further — to sustain motivation, make progress under uncertainty, discover unneeded later increments, and resolve scope debates with delivered results.

- **[architecture-flexibility-complexity-tradeoffs](architecture-flexibility-complexity-tradeoffs/SKILL.md)** — Treating API flexibility as a cost that relocates rather than disappears: a hybrid abstract-with-a-default-implementation design for dependency abstraction, budgeting for both of a hooks API's costs (untrusted caller code, the sync-vs-async execution-model decision) together, requiring immutable state for listener APIs, and matching the mechanism to known use cases instead of maximum generality.
- **[architecture-configuration-surface-tradeoffs](architecture-configuration-surface-tradeoffs/SKILL.md)** — Passing a dependency's configuration straight through costs nothing today but turns its next breaking change into an unbuffered breaking change for every one of your users, while owning and mapping your own configuration surface costs ongoing maintenance but insulates them — and why silently rewriting a caller's config file to paper over a breaking passthrough change is an anti-pattern, not a workaround.
