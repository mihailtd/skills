# Redis Stack in Microservice Architectures

You are an expert in microservice architecture patterns and where Redis Stack fits into them. When a user is designing a microservice system and deciding where caching, rate limiting, shared data, or inter-service communication should live, use this skill to place Redis Stack correctly in the architecture — then route to the command-level skill for the actual implementation (this skill is about *where*, not *how*).

- **API gateway rate limiting.** The API gateway is the single entry point external clients go through, and it's the natural place to enforce rate limits before a request ever reaches an application server — rejecting excess requests at the gateway means backend capacity is never spent on them. Because a gateway is typically deployed as a multi-node cluster, the rate limiter must be externalized (shared state across nodes), not per-node in-memory counting — see `database-redis-rate-limiting` for the actual fixed-window/sliding-window implementation.
- **API gateway caching.** Data every microservice needs — session data, authentication tokens/permissions — is a natural fit for a cache at the gateway level rather than re-fetched or re-validated by every downstream service independently. This reduces latency and duplicated work across the whole request fan-out, not just one service. See `database-redis-session-store` and `database-redis-caching-strategy` for the underlying patterns.
- **Domain-driven design / polyglot persistence: consolidate data models, not services.** Microservice architecture pushes toward each service owning its own data model and, per the domain-driven design principle, its own dedicated datastore — sharing one database across services is generally an anti-pattern (it recouples services that are supposed to be independently deployable and scalable). Redis Stack's relevance here is different: because it's multi-model (Hash, JSON, search, time series, probabilistic structures, Streams — see `database-redis-stack-overview`), a team can use *one* Redis Stack deployment to cover several of a service's own heterogeneous data needs, instead of standing up a separate specialized database per data shape. This reduces the *number of different database technologies* a team operates, without violating per-service data ownership — each service still gets its own logical Redis Stack namespace/instance, it's just not a different product per data shape.
- **Query caching (cache-aside per microservice).** When a microservice's system-of-record database can't serve reads at the latency/throughput the service needs, deploy a cache-aside cache scoped to that one microservice — not a shared cache across services, which would recouple them the same way a shared database would. The pattern: check the cache first; on a hit, return immediately; on a miss, read from the system of record, populate the cache, then return. This keeps caching decisions and cache invalidation local to the one service that understands its own data's freshness requirements. See `database-redis-caching-strategy` for the mechanics (TTLs, stampede protection, atomic get-or-compute).
- **CQRS: separate the durability-optimized write path from the latency-optimized read path.** When one microservice owns the authoritative, durable copy of some data (its system of record — typically a disk-based, ACID database) but other services need that same data available in real time for reads, don't force a single database to serve both needs at once (a database tuned for durable writes is rarely also tuned for the highest possible read throughput, and coupling other services' reads to the write-side database recouples their deployments). Instead: write to the system of record as the durability-critical path, and replicate changes into a Redis cache that other services read from directly. This decouples read scalability from write durability — the read side can be scaled/optimized independently of the write side's consistency requirements. The replication step (keeping the Redis-side copy current as the system of record changes) is the part that needs a deliberate mechanism — e.g. the service publishing change events (see the Streams pattern below) that a consumer uses to update the cache, or an explicit write-through step in the write path itself.
- **Inter-service communication via Streams, not Pub/Sub, when delivery matters.** For microservices exchanging events (order placed, inventory changed, payment confirmed), an event-driven message broker decouples producers from consumers, tolerates disconnection/reconnection, and scales through parallel consumers. Redis Streams (see `database-redis-streams`) is the right structure for this — comparable in role to Kafka topic partitions — specifically because it's persistent and acknowledged, unlike Pub/Sub (see `database-redis-queues-pubsub`), which silently drops events for any subscriber that's disconnected at publish time. **A typical topology is one consumer group per microservice**: every microservice that needs to react to an event stream gets its own group (so every group sees every event independently), while multiple worker instances *within* one microservice's group split the processing load — this maps consumer groups onto service boundaries and consumers-within-a-group onto that service's own horizontal scaling.
- **This is architectural placement guidance, not a replacement for the command-level skills.** Once a pattern above is chosen, implement it using the matching skill (`database-redis-rate-limiting`, `database-redis-caching-strategy`, `database-redis-session-store`, `database-redis-streams`, `database-redis-search-indexing`, etc.) — don't re-derive command syntax here.

## Decision Summary

| Architectural need | Redis Stack role | Implementation skill |
|---|---|---|
| Protect backend services from excess/abusive traffic | Externalized, shared-state rate limiter at the gateway | `database-redis-rate-limiting` |
| Avoid re-fetching session/auth data per downstream call | Gateway-level cache | `database-redis-session-store`, `database-redis-caching-strategy` |
| One service, multiple data shapes | Single multi-model Redis Stack instance per service | `database-redis-stack-overview` |
| A service's DB can't serve reads fast enough | Cache-aside cache scoped to that service | `database-redis-caching-strategy` |
| Durable writes need to be readable in real time elsewhere | System of record (writes) + Redis (reads), kept in sync | `database-redis-streams` (for the sync mechanism) |
| Services need to react to each other's events, reliably | Redis Streams, one consumer group per service | `database-redis-streams` |
