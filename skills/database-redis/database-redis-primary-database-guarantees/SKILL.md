# Redis as a Primary Database: BASE and ACID Guarantees

You are an expert in evaluating Redis's consistency and durability guarantees as an authoritative data store. When a user is deciding whether Redis can be the *primary* database for a use case (not a cache in front of another system of record), guide them through what Redis actually guarantees — precisely, not by reputation — instead of assuming "NoSQL" implies unsuitable for authoritative data, or assuming Redis behaves exactly like a traditional RDBMS.

- **"Primary database" is a role, not a certification** — a database earns it by being the authoritative, most-recent copy of the data (not a read replica or a cache fed by change-data-capture from something else), serving real transactional workloads, surviving single failures via failover/backup, and scaling with load. Redis can fill this role for specific use cases (session stores, auth tokens, online feature stores, geo-positioning, vector search — see the other skills in this package) where it's the *only* database involved, not paired with a separate system of record. It's a poor fit as a wholesale RDBMS replacement for workloads that genuinely need multi-table referential integrity, ad hoc relational queries, or full ACID transaction semantics across arbitrary data.
- **Redis fulfills the BASE properties** (Basically Available, Soft State, Eventual Consistency) rather than strict ACID — this is a deliberate design point most NoSQL stores share, trading strict consistency for availability and performance, not an oversight:
  - **Basically Available** — with replication (Sentinel-managed failover, Cluster, or Enterprise/Cloud), Redis survives a master failure by promoting a replica, rather than going fully unavailable.
  - **Soft State** — stored data can change without direct user action: replication lag causes a replica's state to catch up asynchronously, and (when used as a cache) eviction/expiration change data with no write from any client. Contrast with a "hard state" strongly-consistent system, where data only changes in response to explicit writes.
  - **Eventual Consistency** — Redis replication is asynchronous for performance; a replica can briefly lag behind its master, converging to consistency after that lag closes, not instantaneously on every write. See `database-redis-replication-consistency` for exactly how much this can lose and how to tighten it.
- **Map ACID property-by-property instead of asking "is Redis ACID" as a yes/no** — the honest answer is "partially, deliberately, with specific mechanisms for each property, and real, documented gaps":
  - **Atomicity** — real, via `MULTI`/`EXEC`/`WATCH`, atomic multi-key commands, and Lua/JS functions — but with caveats around crash timing and no automatic rollback. See `database-redis-transactions` for the full mechanics, including where atomicity can still be violated (a corrupted AOF write mid-transaction).
  - **Consistency** (the ACID sense — a transaction can't leave the database logically invalid) — Redis has no schema constraints/referential integrity/cascades to enforce, so this property is trivially satisfied in the sense that there's nothing built in to violate; whatever "consistent" means for the application's data model is entirely the application's responsibility to enforce, not the database's.
  - **Isolation** — weaker than a traditional RDBMS: Redis has no lock manager, so a `MULTI`/`EXEC` transaction doesn't block a concurrent client from changing a key it's about to touch, unless that key was explicitly `WATCH`ed for optimistic-locking-style isolation. See `database-redis-transactions` for the concrete failure mode this produces if `WATCH` is skipped.
  - **Durability** — configurable, not fixed: from "no persistence at all" up to "fsync on every write," with a real, measured performance cost that gets steeper the stronger the guarantee. See `database-redis-persistence-durability` for the concrete settings and their tradeoffs.
- **Don't treat "eventually consistent" as "consistency doesn't matter here."** For use cases where losing a small, recent window of writes on failover is genuinely tolerable (e.g. losing a few seconds of auth tokens just means affected users log in again), Redis's defaults are a reasonable, fast choice. For anything where that loss has a real cost, deliberately dial up durability/replication guarantees (`database-redis-persistence-durability`, `database-redis-replication-consistency`) — don't assume the safety is automatic, and don't assume the strongest settings are "free" performance-wise either; every one of these guarantees is a measured trade against throughput.
- **The honest gap versus a traditional RDBMS, stated plainly**: no transaction manager with configurable isolation levels, no automatic rollback of a partially-applied transaction, no cross-shard/cross-slot distributed transactions in a clustered deployment. These aren't hidden — they're the direct consequence of the single-threaded, low-overhead design that also makes Redis fast. Set expectations accordingly rather than assuming Redis quietly provides RDBMS-grade transaction semantics because it *has* a `MULTI`/`EXEC` command.

## Where to Go for the Mechanics

- **`database-redis-transactions`** — `MULTI`/`EXEC`/`DISCARD`/`WATCH`, what actually gets rolled back versus what doesn't, atomic multi-key commands as a lighter alternative.
- **`database-redis-persistence-durability`** — AOF vs. RDB, `appendfsync` policy tradeoffs (with real benchmark numbers), corrupted-AOF recovery.
- **`database-redis-replication-consistency`** — how asynchronous replication actually works, what a replica lag means for failover, and `WAIT`/`WAITAOF` for tightening the guarantee.
